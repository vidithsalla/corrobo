# corrobo v0.1 — technical spec

Status: accepted design basis for the first implementation. Supersedes nothing in `docs/pressure-test-v0.md`; this is the concrete API derived from it.

## A. Problem

A side-effecting operation (a payment, a ticket mutation, a message, an infra change) can produce an uncertain transport result: a timeout, a dropped connection, a 5xx. The transport result does **not** tell you whether the underlying business effect happened. Treating "the call threw" as "the effect didn't happen" is the specific mistake that causes duplicate side effects on retry.

corrobo's job: separate *what the available evidence establishes* (evidence state) from *what is safe to do next* (recovery disposition), and never let a transport failure alone decide either.

## B. Core lifecycle

```
intent
  → authorization check                            (known action, does it need human sign-off?)
  → persist operation identity + intent            (before any side effect is attempted)
  → reserve the attempt                            (durably, before execute() — see §L)
  → execute()                                       (attempt the side effect; capture transport outcome, don't interpret it)
  → observe()                                       (ask the authoritative source what actually happened; can fail, can be PENDING)
  → reconcile(intent, transport, observation)        (deterministic: → evidence state)
  → decideDisposition(evidence state, attempt number, retry policy, settlement) (deterministic: → recovery disposition)
  → persist attempt + evidence + disposition       (version-checked — see §O)
```

`authorize()` runs before the operation record is created, so an `authorize()` that throws leaves no record and a repeat call simply authorizes again; nothing external has been attempted at that point.

`runEffect()` performs **one lifecycle pass per call** and is safe to call repeatedly with the same operation identity — it will only actually invoke `execute()` when doing so is safe (see §C, "re-entry behavior"). It does not poll, schedule, or retry on its own (see §J).

## C. Core types

```ts
type EvidenceState = "APPLIED" | "NOT_APPLIED" | "CONFLICTED" | "PENDING" | "UNKNOWN";
type RecoveryDisposition = "COMPLETE" | "RETRY" | "REPLAN" | "REVIEW" | "INVESTIGATE";

interface OperationIdentity {
  id: string;          // caller-generated, globally unique for this operation attempt-series
  operationType: string;
}

interface ReasonCode {
  code: string;
  summary: string;
  metadata?: Record<string, unknown>; // duplicateDetected, partiallyApplied, retryExhausted, etc.
}

type TransportOutcome<Evidence> =
  | { ok: true; evidence: Evidence }
  | { ok: false; error: { message: string; raw?: unknown } };

type ObservationResult<Observation> =
  | { status: "observed"; data: Observation; authoritative: boolean; source: string; observedAt: string }
  | { status: "pending"; authoritative: boolean; source: string; observedAt: string; data?: Observation }
  | { status: "observation_failed"; error: { message: string; raw?: unknown }; source: string; observedAt: string };

// Informational only; never read by the runtime (§H).
interface OperationCapabilities {
  nativeIdempotency: boolean;      // the underlying API guarantees idempotent execution given the same identity
  callerGeneratedIdentity: boolean; // identity can be embedded into the request itself
  optimisticConcurrency: boolean;   // reconcile() can reliably detect a conflicting external change
  convergence: boolean;             // PENDING is an expected, normal outcome for this operation type
}

interface RetryPolicy {
  maxAttempts: number;
  retryOnNotApplied: boolean; // the ONLY evidence state that can ever become RETRY — see §E
}

interface EffectContract<Intent, Observation, Evidence> {
  operationType: string;
  capabilities?: OperationCapabilities; // optional, informational (§H)
  retryPolicy: RetryPolicy;
  // Longest time after an attempt starts that its effect could still land; governs when a
  // NOT_APPLIED after a failed transport may be retried (§O). Omitted: INVESTIGATE instead.
  maxInFlightMs?: number;
  authorize?(intent: Intent): { requiresReview: boolean; reason?: ReasonCode } | Promise<...>;
  execute(input: { intent: Intent; identity: OperationIdentity; attemptNumber: number }): Promise<Evidence>;
  observe(input: { intent: Intent; identity: OperationIdentity; transport: TransportOutcome<Evidence>; attemptStartedAt: string }): Promise<ObservationResult<Observation>>;
  reconcile(input: { intent: Intent; transport: TransportOutcome<Evidence>; observation: ObservationResult<Observation> })
    : { evidenceState: EvidenceState; reason: ReasonCode; observedEffect?: unknown };
  // Optional: overrides the default canonical-JSON intent fingerprint used for identity-reuse
  // binding (§K). Provide only if the default would treat two meaningfully different intents
  // as equal, or vice versa, for this operation type.
  fingerprintIntent?(intent: Intent): string;
}

// An attempt's lifecycle is internal/store-facing, not a sixth evidence state or disposition —
// see §L for why RESERVED exists.
type AttemptRecord =
  | { status: "RESERVED"; attemptNumber: number; startedAt: string; updatedAt: string }
  | {
      status: "RESOLVED";
      attemptNumber: number;
      startedAt: string;
      updatedAt: string;
      transport: TransportOutcome<unknown>;
      observations: ObservationResult<unknown>[]; // >1 only when re-observed while PENDING
      evidenceState: EvidenceState;
      evidenceReason: ReasonCode;
      disposition: RecoveryDisposition | null; // null exactly when evidenceState is PENDING
      dispositionReason: ReasonCode;
      retryNotBefore?: string; // only with RETRY after a failed transport, inside the window (§O)
    };

interface OperationRecord {
  identity: OperationIdentity;
  intent: unknown;
  status: "AWAITING_REVIEW" | "OPEN" | "CLOSED";
  attempts: AttemptRecord[];
  blockedBy?: BlockingCheck; // the check that stopped the next attempt (§M.1)
  review?: RecordedReview; // the latest review decision (§M)
  createdAt: string;
  updatedAt: string;
  version: number; // +1 on every write; every store write is version-checked (§O)
}

interface EffectRequest<Intent, Context = unknown> {
  identity: OperationIdentity | string; // a string id uses the contract's operationType (§H)
  intent: Intent;
  context?: Context; // per call, for authorize()/revalidate(); never stored (§M.1)
}
```

`execute()` and `observe()` are caught by the runtime — a thrown exception or timeout becomes `{ ok: false, error }` / `observation_failed`, never an uncaught rejection. `reconcile()` is a plain, deterministic function: same inputs, same output, no I/O.

## D. Evidence states

- **APPLIED** — observation confirms the intended effect exists.
- **NOT_APPLIED** — observation confirms the intended effect does not exist.
- **CONFLICTED** — observation shows authoritative state diverged from what the plan assumed (someone/something else changed it).
- **PENDING** — observation acknowledges the request but the effect has not yet converged; this is a normal, expected outcome for some operation types, not a failure.
- **UNKNOWN** — evidence is insufficient to place the operation in any of the above (observation failed, or produced an ambiguous result).

## E. Recovery dispositions

- **COMPLETE** — done, evidence confirms it.
- **RETRY** — safe to attempt again. The *only* evidence state that can ever produce RETRY is NOT_APPLIED, and only when the contract's `retryPolicy.retryOnNotApplied` is `true`, attempts remain, and the NOT_APPLIED is *settled* (§O) — there is no configuration that makes APPLIED, CONFLICTED, PENDING, or UNKNOWN retryable; `decideDisposition` doesn't read `retryPolicy` at all for those four. A RETRY may carry `retryNotBefore`: `runEffect()` makes no new attempt before that time, and re-observes before making one after it.
- **REPLAN** — the world changed under the plan; a new intent (and new operation identity) is needed, not a retry of this one.
- **REVIEW** — a known, well-formed action requires human authorization before `execute()` is even attempted. This comes from `authorize()`, never from evidence — it is a policy gate, not an uncertain outcome.
- **INVESTIGATE** — evidence cannot support a safe automatic decision (UNKNOWN), retry is exhausted/unsafe for a NOT_APPLIED result, or a NOT_APPLIED followed a failed transport and the contract declares no in-flight window, so a late landing can't be ruled out (§O). Requires a human or an out-of-band process; corrobo will not guess.

## F. Separation of evidence and disposition

Evidence state is a claim about the world, established only from observation. Disposition is a policy decision about what corrobo should recommend next, computed *from* the evidence state plus attempt history, per-operation-type retry policy, and whether a NOT_APPLIED is settled (§O) — never the reverse, and never conflated into one enum. `decideDisposition({ evidenceState, attemptNumber, retryPolicy, settlement })` is the one place this mapping happens, and it is a pure function (see `src/core/disposition.ts`).

PENDING is the one evidence state with no disposition (`disposition: null`) — "no action is safe to recommend yet; re-observe later" is not the same claim as RETRY, REPLAN, REVIEW, or INVESTIGATE, and forcing it into one of those would misrepresent what's known.

## G. Observation quality

`ObservationResult` carries `authoritative: boolean` and `source: string` so a contract can be honest about what kind of read-back it did (a direct authoritative key lookup vs. a best-effort scan of recent history). `observedAt` records freshness. There is no numerical confidence score — the pressure test found no real integration where a manufactured number would mean anything precise; `authoritative`/`source`/the reason-code metadata are the honest granularity available.

**`observe()` must only read.** corrobo calls it where nothing may be executed: during crash recovery, in the re-check before a retry, after an approval expired or a `revalidate()` rejection. A read-back that could itself create the effect, such as replaying the create request with its idempotency key, bypasses review, expiry and `revalidate()` exactly when they apply. Look the result up instead: by the id `execute()` got back, or by a correlation value it attached.

## H. Capabilities

`OperationCapabilities` (optional on a contract) is deliberately small (4 booleans) and describes the *operation type*, not the vendor — the pressure test showed idempotency/versioning support can differ between two operations on the same API (e.g. GitHub's `merge_pull_request` vs. `update_issue`). It is informational only — the runtime never reads it; the retry decision is driven by `RetryPolicy` (and late landings by `maxInFlightMs`), which the contract author sets deliberately per operation type.

Three small helpers cut boilerplate without changing behavior: `defineContract<Intent>()({...})` infers the observation and evidence types (only the intent type is named), `observed(data, { source, authoritative })` builds an observation (with `authoritative` deliberately required), and `reconciled(state, code, summary)` builds reconcile()'s answer. A request's `identity` may be a plain string id, shorthand for `{ id, operationType: contract.operationType }`; an explicit identity whose `operationType` differs from the contract's is rejected before anything happens.

## I. Guarantees and non-guarantees

- corrobo does **not** guarantee exactly-once execution against any third-party system it does not control. It guarantees that its own recorded decision (COMPLETE/RETRY/REPLAN/REVIEW/INVESTIGATE) is derived only from real evidence, never invented.
- corrobo cannot create authoritative evidence where none exists. If `observe()` fails or is ambiguous, the honest answer is UNKNOWN → INVESTIGATE, not a guess.
- UNKNOWN and PENDING are legitimate, final(-for-now) outputs, not bugs to be engineered away.
- Whether a retry is safe is entirely a function of the operation's own semantics (native idempotency, natural idempotency like `PUT`/declarative apply, or none) — corrobo enforces the policy the contract author declares, it does not infer safety on its own.

## I.1 Concurrency: two callers, the same operation identity

`EffectStore` has one coordination method, `tryAcquireLock(identityId)`, returning (on success) a lock bound to its own scoped `store` — every operation a coordinated `runEffect()` pass performs (reservation, reads, the final resolve) runs through that bound store, not the outer one. It is non-blocking: a caller who cannot acquire it does not wait — it returns the operation's current recorded state (or an honest "in progress, call again shortly" placeholder if no state has been recorded yet) rather than retrying or executing on its own.

With **PostgresStore**, this is a session-scoped Postgres advisory lock (`pg_try_advisory_lock`) held on one dedicated pooled connection for the duration of the pass, and that *same* connection is what the lock's bound store uses for every query the pass makes. One in-flight identity therefore consumes exactly one pool connection for its entire pass — never a lock connection plus separate bookkeeping connections, which earlier could exhaust the pool and self-deadlock once concurrently in-flight distinct identities reached `pool.max` (every connection held by a lock, none left for any pass's own reads/writes). If the process holding the connection crashes, Postgres releases the advisory lock automatically — no lease timers, no permanent locks. The flip side: if only the *connection* dies (a network drop, a failover, an idle-session kill) while the process keeps running `execute()`, the lock is released while that pass is still in flight. The lock alone therefore cannot be the safety boundary; §O's version checks and settlement rule are what keep that case from producing a duplicate. Different operation identities hash to different lock keys and never serialize against each other; the connection is not held inside a transaction and takes no row lock, so ordinary reads of the row by other tools are never blocked.

Precisely:

> With `PostgresStore`, concurrent callers using the same corrobo operation identity are coordinated so only one active execution path is allowed at a time. Corrobo durably reserves an attempt before execution (§L): if a worker dies with an unresolved attempt, a subsequent run for that identity observes and reconciles before deciding whether another execution is safe — it never blindly executes again. That subsequent run can itself be UNKNOWN → INVESTIGATE if observation still can't establish the truth; corrobo will not guess.

What this is **not**: a distributed exactly-once guarantee for the external system. Two different application processes still cannot both create a Stripe refund for the same operation identity through corrobo, but corrobo makes no claim about, and has no coordination role over, whatever else might independently call Stripe directly outside of corrobo. A custom `EffectStore` implementation must provide the same same-identity coordination via `tryAcquireLock` to be safe for concurrent use — corrobo cannot enforce this for a store it doesn't control.

`InMemoryStore`'s `tryAcquireLock` is a plain in-process mutex (a `Set` of locked identity ids), and its bound store is just itself. It correctly coordinates concurrent `runEffect()` calls *within one Node process* — useful for a single server handling overlapping requests — but provides no cross-process or distributed guarantee, and no crash durability, whatsoever. Do not rely on it where more than one process could race the same identity, or where a process restart must not risk a duplicate side effect.

## J. Privacy and data persistence

corrobo has no telemetry and no corrobo-operated backend — verified by inspection, not merely stated: nothing in `src/core`, `src/stores`, or `src/testing` makes a network request, logs anything automatically, or references any fixed/maintainer-controlled destination. The only network-capable code in the shipped package is `PostgresStore`'s use of the pool you pass in: corrobo never imports `pg` itself (it's an optional peer dependency), and only ever talks to the `Pool` the caller constructs.

**What `PostgresStore` persists** is exactly the developer-supplied data corrobo's model requires to provide its guarantees: `intent`, transport evidence, observations, reason metadata (including from `revalidate()`), and review decisions (`reviewer`, `note`, times, and the intent fingerprint, which is a canonical copy of the intent unless the contract supplies its own `fingerprintIntent()`), alongside identity/status/timestamps. `EffectRequest.context` is never persisted. corrobo does not inspect, classify, or filter this data — it is generic by design, which is what makes the abstraction framework-agnostic, but it means whatever a contract's `intent`/`observe()`/`reconcile()` produce is persisted verbatim.

**`error.raw` is excluded from Postgres persistence.** `TransportOutcome`'s and `ObservationResult`'s `error.raw` field is the runtime's unfiltered passthrough of whatever a contract's `execute()`/`observe()` actually threw — realistic HTTP client errors commonly attach the original request (including auth headers) and response body (which can carry customer data) to that thrown value. `PostgresStore` strips `error.raw` specifically at its own write boundary — `attempt.transport.error.raw` and `attempt.observations[*].error.raw` — before serializing, keeping only `error.message` (a plain string). This is a narrow, explicit removal of two specific known fields, not a generic secret scanner: corrobo does not attempt to detect "secret-looking" values anywhere else (not in `intent`, not in `observedEffect`, not in reason metadata), because a heuristic like that would create false confidence over data this library has no way to safely judge. The in-memory `TransportOutcome`/`ObservationResult` objects a contract's own `reconcile()` receives are unaffected by this — the removal happens only at `PostgresStore`'s serialization boundary, after reconciliation has already run.

**Persisted records do not automatically expire.** There is no TTL, retention policy, or delete API in v0 — retention and deletion are the developer's own responsibility, on the Postgres database they operate. This is a deliberate v0 boundary (see §N), not an oversight: a library persisting into infrastructure the developer fully owns should not unilaterally impose a retention policy.

**Constructing `PostgresStore` requires an explicit acknowledgement** — `new PostgresStore(pool, { acknowledgePersistence: true })` — enforced both by the type system (`acknowledgePersistence` is typed as the literal `true`, not `boolean`) and at runtime (a plain-JS or `any`-typed caller passing anything else throws immediately, before any query is possible). This is a one-time code-level opt-in, not a prompt, not telemetry, and not a network permission — its only purpose is making "this durably persists your data" a deliberate choice rather than an implicit side effect of importing a class. `InMemoryStore` requires no such acknowledgement, since it never persists anything beyond the current process; `PostgresStore.migrate()` also requires none, since creating a schema is not itself persisting any application data.

## K. Identity must bind to the same intended effect

Looking up an operation by `identity.id` alone is not sufficient: nothing stops an application bug from reusing the same id string for two logically unrelated requests (a different `operationType`, or the same type with a different intent — e.g. `refund:123` first meaning "refund $50," then accidentally meaning "refund $500"). Silently returning the first operation's cached result for the second would be exactly the kind of false-COMPLETE this project exists to prevent.

`runEffect()` therefore checks, whenever an existing operation is found for an identity: `operationType` must match the contract being run, and a fingerprint of the intent must match a fingerprint of the originally-persisted intent. On any mismatch it throws a specific, loud error before `execute()`/`observe()` are ever reached — never a silent wrong answer. The fingerprint defaults to a stable, key-sorted JSON serialization (`canonicalStringify`, object key order doesn't affect it, array order does) computed from the intent's stored form. `runEffect()` reads the intent exactly once per call, through JSON semantics, and both persists and fingerprints that one reading — so what is fingerprinted is always what a store persists, even for an object that would read differently a second time: a `Date` fingerprints as its ISO string and still matches itself after a Postgres round trip. Intents that JSON stores identically are therefore the same intent (`{ a: undefined }` and `{}`, `NaN` and `null`, a `Date` and its ISO string). Values JSON would silently lose, mangle, or store as something else — circular references, functions, symbols, BigInts, Maps, Sets, typed arrays, ArrayBuffers, own getter properties, or `undefined` as the whole intent — are rejected with a `TypeError` naming the path. With the default fingerprint, `runEffect()` checks this before doing anything else, so such an intent never reaches `execute()`. A contract that supplies `fingerprintIntent()` takes responsibility for its own intents (the store must still be able to persist them). It can be overridden per contract via `fingerprintIntent(intent)` for the rare case where that default treats two intents as equal (or different) incorrectly for a given operation type.

The practical rule: **the same operation identity must always represent the same logically intended effect.** Don't include values in an intent that are irrelevant to what the operation actually *does* but change on every call (a fresh timestamp, a request-tracing id, a random nonce) unless you also provide a `fingerprintIntent` that ignores them — otherwise every retry of the same logical operation will look like a different one and trip the conflict check. Conversely, don't put secrets (API keys, tokens) in the intent purely for identity purposes — the intent is persisted as part of the operation record, in plaintext, by whichever store you use.

## L. Crash-safe attempt reservation

Before this was added, the window between creating an operation record and persisting its first attempt's outcome was unrecorded: a crash inside that window left an `OPEN` record with zero attempts, indistinguishable from an operation that was never attempted at all — and the next call would call `execute()` again. For an operation type without native idempotency, that's a real duplicate side effect, caused by nothing more than a restart.

Corrobo now durably reserves an attempt (`status: "RESERVED"`, just an attempt number and start time) *before* `execute()` is ever called, and resolves it in place afterward. If a run finds a reserved-but-unresolved attempt (a prior process died mid-attempt), it does **not** call `execute()` again — it goes straight to `observe()`/`reconcile()`, using an honest "transport outcome unknown" value in place of real transport evidence (the same shape already used for a genuine `execute()` throw — this is not fabricated evidence, it truthfully states that no outcome was ever recorded). From there the normal evidence → disposition mapping applies exactly as it would for any other attempt: APPLIED → COMPLETE, CONFLICTED → REPLAN, PENDING → continue re-observing, UNKNOWN → INVESTIGATE if observation still can't resolve it either way — and NOT_APPLIED follows the settlement rule (§O), because the dead attempt's request may still be in flight: without a declared `maxInFlightMs` it is INVESTIGATE, never an automatic retry. This lifecycle (`RESERVED` → `RESOLVED`) is a store-internal concept — it does not add a sixth evidence state or disposition.

## M. Review decisions

A `REVIEW` gate that a human declines is a normal, expected outcome — the whole point of a review gate is that sometimes the answer is no. Rejection closes the operation terminally *without ever calling* `execute()`, recorded via a `POLICY_REVIEW_REJECTED` reason code. Repeated calls after rejection stay `CLOSED` and never execute. Rejection is a pre-execution policy decision, not reconciliation evidence — it is represented as a `REVIEW`-disposition result whose `status` is `CLOSED` rather than `AWAITING_REVIEW`, not as a sixth disposition.

In an agent runtime the approval *is* the safety boundary, so it has to be attributable, bound to exactly what was reviewed, checkable later, and out of reach of the code that acts. Deciding and acting are therefore two calls:

```ts
// The worker or agent runtime: the result reports AWAITING_REVIEW with a reviewToken.
const waiting = await runEffect(store, contract, { identity, intent, context: { actor: "worker" } });
// ...your app queues a review task with the intent and waiting.reviewToken...
// The review screen (your own, authenticated flow): records the decision, never executes.
await reviewEffect(store, contract, {
  identity,
  decision: { decision: "approved", reviewer: "alice@example.com", reviewToken, expiresAt: "2026-10-02T12:00:00Z" }
});
// The worker (or the agent's runtime): acts on it, checking the approval before every attempt.
await runEffect(store, contract, { identity, intent, context: { actor: "worker" } });
```

A `ReviewDecision` is `{ decision: "approved" | "rejected"; reviewer: string; reviewToken: string; decidedAt?; expiresAt?; intentFingerprint?; note? }`. `runEffect()` takes no decision at all (a value in 0.3's `reviewDecision` field throws a `TypeError` pointing here). That is an API boundary, not a privilege boundary: any code holding the store and contract can import `reviewEffect()` and name any reviewer. It enables capability separation (a review service that alone calls `reviewEffect()`, its own database role, signed decisions) but doesn't provide it by itself.

`reviewEffect()` takes the operation's lock: if another call holds it, it throws `OperationBusyError` and records nothing. Like `runEffect()`, it waits for a store connection if the pool is exhausted, then re-reads and re-checks everything under the lock. If it won't record the decision it throws `ReviewNotAcceptedError`, with a `.code` and the operation's `.current` state, and records nothing; it never returns quietly without recording. After an approval, its result is `REVIEW_APPROVED` (approved, not attempted since), even when earlier attempts exist.

- **One decision answers one review.** Every time an operation goes to review (`authorize()` at creation, `revalidate()` asking for review, an approval that expired or can't be attributed), corrobo opens a new *review episode*: a generation number, the store-clock time it began, and an opaque token bound to the operation, that episode and the recorded intent's fingerprint. The token is returned as `EffectResult.reviewToken` while the operation awaits review, and a decision must carry it. A token from an earlier review or another operation is refused (`STALE_REVIEW_TOKEN`), as is a `decidedAt` earlier than the current review's start (`DECIDED_BEFORE_REVIEW_OPENED`; compare clocks with care, or omit `decidedAt` to use the store's). A decision on an operation that isn't awaiting review is refused too (`NOT_AWAITING_REVIEW`). The token (a digest that includes a random nonce, so no two reviews share one) is a binding, not a secret: it doesn't authenticate anyone. A review that a recorded decision already answered (one carrying its token, or any decision recorded after it opened, such as a 0.4.0 worker's) is used up: its token never counts again, and if the operation is back awaiting review without a new episode (a 0.4.0 worker during a rolling upgrade), the next `runEffect()` opens one. An operation that went to review before tokens existed gets one the same way. An approval counts toward an attempt only if it answered the operation's current review, so approvals recorded by 0.4.0 (no token) send the operation back to review (`APPROVAL_NOT_RECORDED`).

- **Validated before anything runs.** A missing or empty `reviewer`, an `expiresAt` on a rejection or not after `decidedAt`, or a time that isn't a strict RFC 3339 timestamp with `Z` or an explicit offset (a local time without an offset would mean different instants on different hosts) all throw a `TypeError`, and nothing is recorded or executed. Valid times are stored in canonical UTC form.
- **Bound to the recorded intent.** corrobo records the decision on the operation (`OperationRecord.review`, also returned as `EffectResult.review`) with the fingerprint of the recorded intent and the time it recorded it (store clock). If the caller passes the `intentFingerprint` of what the reviewer was shown (`fingerprintIntent(contract, intent)`) and it differs, the decision is refused (throws) and nothing changes.
- **Checked before every attempt.** Before each attempt made under an approval, corrobo itself checks that it still applies to the recorded intent (`APPROVAL_INTENT_MISMATCH` otherwise, e.g. after the contract's fingerprint rules changed) and hasn't expired (`APPROVAL_EXPIRED`). Either sends the operation back to `AWAITING_REVIEW` without executing. Then `revalidate()` (§M.1) receives the approval to check your own approver policy: who may approve what, whether the approver is the requester. The approval is checked once more after `revalidate()` returns, against the store-clock reading the attempt is then reserved with (its `startedAt`), so an approval is never used for an attempt whose recorded start is at or after `expiresAt`. As with `revalidate()`, the reservation write still sits between that reading and `execute()`; if a few milliseconds matter, leave margin in `expiresAt`.
- **Approvals age out.** A contract's `maxApprovalAgeMs` bounds how long any approval covers new attempts, counted from when it was decided (or recorded, if earlier), whether or not the decision set `expiresAt`; the earlier of the two wins. An approval older than that when it arrives is refused (`APPROVAL_ALREADY_EXPIRED`), and one that ages out before an attempt sends the operation back to review (`APPROVAL_EXPIRED`). Without it, an approval with no `expiresAt` covers every later attempt of the operation: the reviewer approved the effect, not one call.
- **Approvals from 0.3.x.** An operation that left review under 0.3.x has no recorded decision, so before any further attempt it goes back to `AWAITING_REVIEW` with `APPROVAL_NOT_RECORDED`.
- **Re-observed after the wait.** An approval that follows earlier attempts (because `revalidate()` sent attempt N to review) records how many attempts preceded it, and the next `runEffect()` re-observes the latest one before executing again, even if its `NOT_APPLIED` was final when recorded.
- **Recorded on the attempt.** The approval in force is copied onto each attempt it allowed (`attempt.check.approval`), so "who allowed attempt 2?" is answerable from the record. `context` in `revalidate()` is whoever is executing now, so "the approver isn't the requester" is a direct comparison.
- **What corrobo doesn't do:** authenticate the reviewer. `reviewer` is whatever your app says it is; call `reviewEffect()` only from your own review flow, never from anything a model can call.
- **`context` must be trusted.** A policy in `revalidate()` such as "the approver isn't the actor" is only as good as `context`. Build it on your server from your own session or job data, never from a model's tool arguments.

## M.1 Revalidation before each attempt

`authorize()` answers one question, once, when the operation is recorded: does this action need sign-off? A second question needs asking before *every* attempt: is it still valid to do this now? Between "the model proposed", "a person confirmed" and "attempt 2 after a retry window", the order may have been cancelled, the caller's scope may have changed, an approval may have expired. That is `revalidate()`.

- **Order:** observe/settle → reconcile → `revalidate()` → reserve → execute. It runs under the operation's lock, before every attempt including the first, and before `reserveAttempt`, so a "no" never leaves a reserved attempt that recovery would have to treat as an unknown outcome.
- **It gates new effects only.** It is never consulted while finding out what an earlier attempt did: a settlement re-check that finds a late landing resolves to APPLIED → COMPLETE even if `revalidate()` would now refuse. Crash recovery of a reserved attempt doesn't call it either (nothing executes).
- **Input:** the intent, identity, the attempt number about to be made, the record as it stands, and `context` from *this* call (`EffectRequest.context`: who is calling, with what scope). By attempt 2 the caller may be a background worker, not the user who started it. `context` is never stored or fingerprinted.
- **Outcomes:** `proceed` → reserve and execute; the check is recorded on the attempt (`attempt.check`). `requiresReview` → `AWAITING_REVIEW` / `REVIEW` with its reason; after approval the latest attempt (if any) is re-observed first, even if its `NOT_APPLIED` was final when recorded, because time has passed, and `revalidate()` runs again before executing. `reject` → `CLOSED` / `REPLAN`: the action needs a fresh decision and a new identity. Evidence from earlier attempts is still reported.
- **Failure fails closed without closing:** if it throws or returns anything other than a valid result, nothing is executed, the operation stays `OPEN` with `REVALIDATION_FAILED`, and the next call checks again.
- **Recorded:** a check that stops an attempt is kept on the operation (`OperationRecord.blockedBy`, with the record version it was written at; any later write supersedes it).
- **Keep it fast and bounded.** It runs while the operation's lock is held, and with `PostgresStore` while one pool connection is checked out for this pass. Give any network call inside it a timeout; a slow `revalidate()` holds that connection and makes other callers for the same operation see it as busy. If it times out, throw: that fails closed.
- **It narrows the window; it doesn't close it.** State can change between `revalidate()` and `execute()`. Where the provider supports conditional writes (a version or ETag precondition), use them in `execute()` as well.

## N. What v0 deliberately does not do

- No generic polling/orchestration engine. PENDING is modeled and re-observation is supported (calling `run()` again against a PENDING operation re-observes without re-executing), but scheduling *when* to call `run()` again is the caller's job until multiple real integrations justify generalizing it.
- No maintained third-party connectors (Stripe/Slack/GitHub/Linear/Kubernetes). The examples (generic REST, Stripe refunds, Jev) are examples, not supported adapters.
- No queues, workers, background schedulers, or cloud features.
- The Agent Skill (`skills/corrobo`) is an optional integration aid, not part of the runtime.

## O. Fencing and settlement: when the lock is not enough

Two facts make a lock alone insufficient. First, a Postgres session lock is released when its *connection* dies, even if the process holding it is still inside `execute()`. Second, a request that failed at the transport level (a timeout, a reset) is abandoned by the client, not undone at the provider: it can still land after corrobo has already observed "not applied". Without the two mechanisms below, either fact allows this sequence: pass A reserves attempt 1 and is still inside `execute()`; pass B recovers attempt 1, observes NOT_APPLIED, records RETRY; pass C executes attempt 2; A's request lands too — two effects.

**Fencing (store level).** Every `OperationRecord` has a `version` (0 on create, +1 on every write). Every store write names the version it read and is applied only if it still matches; otherwise it throws `StoreConflictError` and changes nothing (a duplicate create is a conflict too, with `expectedVersion: null`). So a pass that lost its lock can never overwrite what another pass recorded, and cannot reserve a second attempt on top of one another pass already reserved. `runEffect()` treats a conflict as "this pass no longer owns the operation" and returns the record as it now stands. `PostgresStore` implements this with `UPDATE … WHERE id = $1 AND version = $n`; custom stores must do the same atomically.

**Settlement (decision level).** A NOT_APPLIED is *settled* — final enough to retry on — when execute() returned a response (the request is no longer in flight), or when the attempt started at least `maxInFlightMs` ago. `maxInFlightMs` is an optional contract field: the longest time after an attempt starts that its effect could still land (client timeout plus provider-side processing). The mapping for NOT_APPLIED with retry permitted and attempts remaining is:

| transport | `maxInFlightMs` | now vs `startedAt + maxInFlightMs` | disposition | reason code |
|---|---|---|---|---|
| response received | any | any | RETRY | `SAFE_RETRY` |
| failed / unknown | not declared | — | **INVESTIGATE** | `IN_FLIGHT_NOT_RULED_OUT` |
| failed / unknown | declared | at or after | RETRY | `SAFE_RETRY` |
| failed / unknown | declared | before | RETRY + `retryNotBefore` | `SAFE_RETRY_AFTER_SETTLEMENT` |

For a RETRY with `retryNotBefore`, `runEffect()` does nothing before that time (no execute, no observe, no write). After it — and for any RETRY that followed a failed transport, including ones recorded by 0.2.x — it first re-observes the same attempt and re-decides under the current rules: a late landing then reads APPLIED → COMPLETE with no new attempt; only a settled NOT_APPLIED proceeds to a new attempt, in the same call.

**One clock.** The attempt's start time and the "has the window passed?" check may be read by different processes on different hosts, so both come from the store's clock when it provides one (`CoordinatedStore.now()`). `PostgresStore` reads the database server's `clock_timestamp()`, so host clock skew does not move the window. A custom store without `now()` falls back to each process's local clock — acceptable on a single host only.

Each attempt records the window it was sent under, and settlement for it never uses a shorter one: a deploy that shortens `maxInFlightMs` must not let a request already in flight be retried early (a deploy that removes it makes the attempt `INVESTIGATE`, as declared). An invalid window (negative, NaN, infinite) is refused before anything runs.

`maxInFlightMs: 0` declares that a late landing can never cause a second effect — honest only when re-execution is deduplicated by the provider (an idempotency key that stays the same across attempts, as in the Stripe example, within the provider's key-retention window) or the request provably never left the process.

What this still does **not** cover: a `maxInFlightMs` that is too small for the real provider (the provider's clock and queues are outside corrobo's view — choose it with margin); an `observe()` that reports NOT_APPLIED when it merely failed to find the effect (a search that cannot prove absence must return UNKNOWN); and writes to the external system made outside corrobo.

**Upgrading from 0.2.x.**
1. Stop or drain every 0.2.x worker before any 0.3 worker serves traffic. 0.2.x writes neither check nor bump `version`, so a mixed fleet is not fenced.
2. Run `PostgresStore.migrate(pool)` once. It adds `version BIGINT NOT NULL DEFAULT 0` in place; existing rows start at 0. On PostgreSQL 11+ adding a column with a constant default does not rewrite the table, but it does take a brief `ACCESS EXCLUSIVE` lock on `corrobo_operations`, which queues behind long-running queries on that table — run it with a `lock_timeout` in your normal migration window.
3. Existing records keep working. A RETRY that 0.2.x recorded after a transport failure is settled under the new rules on its next run (see above). Contracts that relied on an immediate RETRY after a transport failure now get INVESTIGATE until they declare `maxInFlightMs`.
4. Custom `EffectStore` implementations must add `version` and version-checked writes (and should add `now()` if used across hosts).
